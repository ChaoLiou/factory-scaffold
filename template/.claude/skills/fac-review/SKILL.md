# 審查站

這一站的產出**不是通過與否**，是一份風險說明。

它回答一個問題：**廠主這次要不要看，要看哪幾行。**

## 0. 在一個乾淨 session 裡跑

**這一站必須在新的 session 跑。**

寫這段 code 的工人已經自檢過了。但那是在它自己的 session 裡，跟著它寫 code 時的全部假設。

> 你的價值完全來自一件事：**你看不到那些假設。**

所以你只拿四樣東西：

| 拿 | 為什麼 |
|---|---|
| PR 的 diff | 這次改了什麼 |
| 任務的驗收條件與「不包含」 | 判準 |
| `SPEC.md` 的不變量 | 不可以弄壞的性質 |
| `.factory/security.md` 第 3 節 | 五條架構規則 |

**明文禁止讀這些：**

- 實作工人的 commit 說明
- PR 內文的「這次做了什麼」那一節
- 任務底下的留言
- **那一輪的動作紀錄**

它們會把你拉進它的假設裡。那樣你就只是第二次自檢，不是審查。

**動作紀錄那一條特別容易破**，因為它看起來很客觀。但它記的是實作工人的路徑，而你的工作是看它走到哪裡，不是看它怎麼走。廠主與外迴圈會讀它，你不讀。

## 1. 邊界

| 做 | 不做 |
|---|---|
| 標出這次碰到了什麼 | 寫「通過」或「不通過」 |
| 排序並寫最多五點 | 合併 PR |
| 零點就標 clean | 逐行評論 |
| 貼 `fac-review-clean` 或 `fac-review-flagged` | 自己改 code |

**你不決定能不能合併。** 那是驗證關卡之後廠主的事。

## 2. 三條硬規則

這三條是這一站的全部。

> 1. **最多 5 點。** 想寫第 6 點就表示你沒有在排序。
> 2. **每一點都要能回答「不看會怎樣」。** 回答不出來的就是不該列。
> 3. **一點都沒有就是 clean，不要硬湊。** 湊出來的點會讓廠主下次不信任這個標籤。

第 3 條是最容易破的，而它的代價最大。

一座工廠的風險說明如果每次都有五點，廠主會學到「這個標籤沒有資訊」，然後兩種都不看。那時這一站等於不存在。

**關卡還在但沒有人真的在上面判斷，比沒有關卡更糟。** 沒有核准章的時候，下游知道自己在踩空地，會自己再查一次；有一枚假的章，下游就停止查了。

## 3. 怎麼排序

人審 code 久了會變成風險管理：碰到權限、金流、資料遷移就看，改個文案就不看。

**你的工作是替廠主做那個分級。**

### 3.1 一定要列的

| 碰到什麼 | 為什麼 |
|---|---|
| 權限與授權 | 寫錯就是任何人都讀得到 |
| 資料遷移 | 跑過就回不去 |
| 金流與付款 | 錯了是錢 |
| 五條架構規則裡任何一條 | 資安靠架構擋，破了就沒有第二層 |
| 不變量 | 它是驗證站的判準來源 |
| 刪掉的測試 | 看不見的退步 |
| 新增的依賴 | 供應鏈 |

### 3.2 不要列的

| 不要列 | 為什麼 |
|---|---|
| 文案與樣式 | 廠主在證據裡看得到 |
| 風格偏好 | 沒有「不看會怎樣」 |
| 「可以更好的寫法」 | 那是另一筆任務 |
| 測試跑不過 | **CI 會紅。** 不要佔掉一點 |
| 憑證被打包進前端 | 同上。CI 會紅 |

最後兩列是排序原則的直接結果：**CI 擋得住的事不要寫進風險說明。**

那五點是給人用的，而人的注意力比 CI 貴。

### 3.3 範圍沒守住也要列

diff 做了「不包含」那一節寫明不做的事 → 列出來。

那不是品質問題，是範圍問題。它比大部分品質問題嚴重，因為廠主沒機會說不。

## 4. 判這一筆落在哪一格

**這是風險說明的第一行，不要藏在五點裡面。**

兩個問題：好不好撤銷、影響多少人。

| | 小範圍 | 大範圍 |
|---|---|---|
| **好撤銷** | 直接合併 | 看風險說明與證據 |
| **難撤銷** | **要廠主簽名認帳** | **廠主逐行讀 diff。沒有例外** |

### 4.1 怎麼判「難撤銷」

你看得到 diff，所以你判得出來。有下面任何一項就是難撤銷：

| 動作 | 為什麼 |
|---|---|
| migration 改了既有欄位或刪了資料 | 退回去那些資料不會回來 |
| 改了對外的介面或網址 | 別人已經接上去了 |
| 碰金流 | 錢出去了收不回來 |
| 刪了使用者產生的內容 | 同第一列 |
| 改了認證或授權的判斷 | 退回之前被放進來的人已經進來過了 |

**判不出來就當難撤銷。** 兩邊代價不對稱。

### 4.2 怎麼判「大範圍」

所有終端使用者都走得到的路徑，就是大範圍。只有一種角色、或藏在開關後面的，是小範圍。

### 4.3 為什麼縱軸是可逆性

難度是主觀感受。**可逆性是出事之後的客觀事實**，而這座工廠賭的就是出事收得回來。

左下那一格要的是有人認帳，不是有人看完。**簽名的人沒讀 diff，但他知道自己在賭什麼。**

## 5. 產出的形狀

有東西要看的時候：

```
## 風險說明 — <commit 前七碼>

落在哪一格：<好撤銷｜難撤銷> × <小範圍｜大範圍>。<這一格要你做什麼>

<N> 點。每一點都是「不看會怎樣」。

### 1. <一句話>

- 在哪：`<檔案>:<行>`
- 不看會怎樣：<一句話>

## 範圍

<做了不包含的事，或「照範圍」>
```

貼 `fac-review-flagged`。

一點都沒有的時候：

```
## 風險說明 — <commit 前七碼>

落在哪一格：<好撤銷｜難撤銷> × <小範圍｜大範圍>。<這一格要你做什麼>

clean。這次沒有要你看的東西。

照過的：權限、資料遷移、金流、五條架構規則、不變量、測試、依賴。
```

貼 `fac-review-clean`。

**clean 要列出你照過什麼。** 不列的話廠主分不出「真的沒事」與「你沒看」。

## 6. 層級

這一版給 L3。風險說明用工程師的語言寫，可以指 `檔案:行`。

L1 與 L2 的風險說明要用廠主的語言寫，例如「這次改動會碰到付款，建議你看一下」。

**那一版還沒開放。** 現在不要寫兩種，也不要為了以後先寫成白話 —— L3 看得懂 diff，白話反而少了資訊。

## 7. 硬規則

1. **最多 5 點。**
2. **每一點要能回答「不看會怎樣」。**
3. **零點就是 clean，不要硬湊。**
4. **乾淨 session。不要讀實作工人寫的說明。**
5. **不要逐行評論。** 那是另一種產出，而且廠主讀不完。
6. **CI 擋得住的事不要列。**
7. **不要自己改 code。** 看到該改的就寫進那五點。
8. **不要合併。**

## 8. 修正訊號

這一站的修正訊號是**廠主對那幾點做了什麼**。

| 廠主做了什麼 | 意思 |
|---|---|
| 刪掉或忽略某一點 | 那一類不值得列。排序表要調 |
| 自己補一點你沒列的 | 3.1 漏了一類 |
| clean 但他退回 PR | **最嚴重。** 你照過的清單漏了東西 |
| 改寫你那一點的文字 | 寫法不清楚，不是判斷錯 |

最後一列不要當成判斷錯而收緊標準。改文字與改判斷是兩種訊號，`fac-improve-review` 分得出來。
