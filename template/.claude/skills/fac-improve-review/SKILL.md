# 外迴圈 — 審查站

這一份看「廠主對那幾點做了什麼」，並提案修改 `fac-review`。

<!-- fac:shared:start -->
<!-- 這一份由腳手架維護。不要改。改了升級會停下來回報。 -->

## 0. 四條共同規則

與 `fac-improve-triage` 第 0 節相同。一次最多兩條、沒點頭不准改、一次性的丟掉、改動與帳本同一個 commit。

## 1. 撈什麼訊號

### 1.0 動作紀錄每週都要讀

修正訊號要等人出手。**動作紀錄不用** —— 它每一輪都產生，而且它記得人沒注意到的那些失敗。

| 從動作紀錄看 | 意思 |
|---|---|
| 同一站反覆重試 | 那一站的判準寫得不清楚 |
| 為了一件小事讀了半個 repo | 脈絡沒指路 |
| 一直在同一個地方停下來回報 | 規則之間打架，或少了一條 |

兩個一起看才完整：修正訊號說「人覺得哪裡不對」，動作紀錄說「工人在哪裡卡住」。見腳手架的 `docs/factory.md` 4.3。


| 訊號 | 在哪看 | 意思 |
|---|---|---|
| A | 廠主刪掉或忽略某一點 | 那一類不值得列。排序表要調 |
| B | 廠主自己補一點你沒列的 | 「一定要列的」漏了一類 |
| C | **標了 clean 但 PR 被退回** | 照過的清單漏了東西 |
| D | 廠主改寫某一點的文字 | 寫法不清楚，不是判斷錯 |
| E | 連續幾輪都剛好五點 | **在硬湊。** 見第 3 節 |

## 2. 訊號 C 最重要

`fac-review-clean` 的意思是「這次沒有要你看的東西」。

標了 clean 而 PR 被退回，表示那句話是假的。

**一次就要提。** 不要等三次。

廠主對 clean 的信任是這一站存在的理由。信任掉了之後，兩種標籤他都不看，這一站等於不存在。

## 3. 訊號 E 怎麼看

連續幾輪都剛好五點，有兩種可能：

| 可能 | 怎麼分 |
|---|---|
| 真的每次都有五件事要看 | 看廠主有沒有真的去看那五點 |
| 在硬湊 | 廠主開始忽略後面兩點 |

第二種的處理方式不是「把上限改成三」。上限不是問題，排序是問題。

**要改的是「一定要列的」與「不要列的」那兩張表，不是那個數字。**

## 4. 訊號 A 與 B 是一對

A 的意思是列太多。B 的意思是漏了。

兩個同時出現的時候，不要兩條都提。看是同一個原因造成的沒有：

- 同一類東西列了又漏 → 那一類的判準寫得不清楚。一條提案。
- 兩類不相干 → 兩條提案。那就滿了這一輪的額度。

## 5. 提案與留帳

形狀與 `fac-improve-triage` 第 3、4 節相同。

要改 `fac-review` 的時候：**產出一個對腳手架的 PR，不要本地改。**

留帳在 `docs/factory-log.md`，與零件改動同一個 commit。

## 6. 硬規則

1. **一次最多兩條。** 那是改動的數量，不是方向 —— **刪掉一條沒有咬到東西的規則，跟加一條新規則一樣是改善。**
2. **沒點頭不准改。**
3. **訊號 C 一次就提。** 其他的照三次門檻。
4. **不要用改數字解決排序問題。**
5. **共用檔案走 PR。**
6. **提案要跑重播集。** 改之前跑一次，改之後跑一次。沒有差別的那一條丟掉。見腳手架的 `docs/factory.md` 7.2。
7. **提案要回答「這一條會不會讓某個指標變好而產品沒變好」。** 四個指標都有那條路，見 `docs/factory.md` 8.2。
