# 實作站

這一站寫 code，產出一個 PR。

**它上面沒有人。** 下一站是審查關卡，所以這一站的輸出要給人看，不是給人改。

## 0. 先讀

| 讀什麼 | 拿什麼 |
|---|---|
| `CONTEXT.md` | 名詞。兩節都讀 |
| 這筆任務的內文 | 要做什麼，以及**不包含**什麼 |
| `specs/<feature>/` | 有規格的話，讀三份 |
| `docs/tech-spec.md` | 架構規則與目前的形狀 |
| `.factory/security.md` 第 3 節 | **碰資料之前。五條架構規則** |
| `SPEC.md` 的不變量 | 不可以弄壞的那些性質 |

## 1. 邊界

| 做 | 不做 |
|---|---|
| 寫 code | 合併 PR |
| 寫測試 | 部署 |
| 開 PR | 改 `.claude/skills/fac-*` |
| 在 `tasks.md` 勾掉做完的 | 改 `SPEC.md` 的不變量 |
| 寫 `_偏離原計畫_` | 改 `.factory/` 底下任何東西 |

最後兩列是硬界線。那些檔案是共用的，改了升級會停下來。

要改它們就走外迴圈：產出一個對腳手架的 PR。

## 2. 在隔離的地方做

一筆任務一個 `git worktree`。

| 為什麼 | |
|---|---|
| 並行 | 幾筆任務同時做，不互相踩 |
| 乾淨 | 每一輪從已知狀態開始 |
| 可丟 | 做壞了整個 worktree 丟掉，不留痕跡 |

做完之後 worktree 要清掉。它不是記憶層，裡面的東西不留存。

## 3. 這一站怎麼跑

五步，照順序。**不要跳過第二步。**

### 3.1 讀任務，列出範圍

寫下兩張清單：要做的、**不包含的**。

「不包含」那一張從 `requirements.md` 的範圍界定抄，或者從任務內文抄。

沒有規格的簡單任務也要列。列不出來就表示它不是簡單任務 —— 退回 `fac-needs-spec`。

### 3.2 確認現況

**先看 code 現在長什麼樣，再動手。**

| 要確認 | 為什麼 |
|---|---|
| 這件事是不是已經做過一半 | 做兩次會衝突 |
| 這塊 code 的慣例 | 不要在一個用 A 寫法的檔案裡寫 B |
| 相鄰的東西會不會被弄壞 | 不變量不在你這次的範圍裡，但它照樣要成立 |

這一步最常被跳過，而跳過的代價是寫出一段「非常一致地做錯事」的 code。

### 3.3 先寫測試

照 `design.md` 第 9 節的 Testing Strategy。沒有規格就照 `docs/tech-spec.md` 的慣例。

**先寫測試，再寫實作。** 順序反過來，測試會長成「證明我寫的 code 跑得起來」，而不是「證明驗收條件成立」。

### 3.3.1 每一條測試要先紅過

**不會失敗的測試保護不了你。** 它只是裝飾，而且它會讓下一輪的人以為這裡有保護。

所以順序是三步：寫測試 → **看它紅** → 寫實作到它綠。沒紅過的那一條要當成還沒寫。

寫完之後再自己試一次：把實作裡那一行的判斷反過來，看測試會不會紅。不會紅就表示那條測試沒有咬到東西。

### 3.4 實作

一次做一個任務。做完一個就在 `tasks.md` 勾掉。

碰資料的時候，`.factory/security.md` 第 3 節那五條規則一條都不能破：

1. 前端不持有任何憑證。資料查詢一律走 server。只准 PKCE flow。
2. 預覽與生產是不同專案、不同帳號。
3. 測試帳號只開在預覽專案。
4. 預覽的位置不可猜測。
5. 生產密鑰不進你的執行層。

**這五條裡任何一條做不到的時候，停下來回報。** 不要找替代寫法繞過去。

### 3.4.1 偏離原計畫要寫下來

實作跟設計不一樣的時候，在 `tasks.md` 那個任務底下寫一行：

```
_偏離原計畫：<發生什麼、改成怎麼做>_
```

**不要去改 `design.md` 假裝當初就這樣想。**

那一行是外迴圈的訊號。改掉設計，訊號就不見了。

### 3.5 開 PR 之前自檢

逐條對 `tasks.md` 的「可觀察完成狀態」。

| 情況 | 怎麼辦 |
|---|---|
| 每一條都從外面看得到 | 開 PR |
| 有一條看不到 | **不要開 PR。** 回去做完，或者寫清楚為什麼做不到 |

「我覺得做完了」不算。那一行要的是從外面看得到的狀態。

## 4. PR 的形狀

```
## 這次做了什麼

<一句話>

## 對到哪幾條驗收條件

- <條號>：<一句話>

## 不包含

<從範圍界定抄過來的那幾條>

## 可觀察完成狀態

| 任務 | 狀態 | 怎麼看 |
|---|---|---|

## 工廠回饋

<卡住的地方。沒有就寫「沒有」>
```

開完 PR 貼 `fac-in-pr`，並撕掉 `fac-ready`。

### 4.1 「工廠回饋」寫給外迴圈

值得寫的四種：

1. 規格少一塊，你猜了。
2. skill 講的事與 code 的實際樣子對不上。
3. 同一種東西每次都要手動補。
4. 架構規則與任務要的東西衝突。

一次性的事不要寫。外部服務壞掉、網路斷了都不是工廠問題。

## 5. 硬規則

1. **只做任務寫明的事。** 「不包含」那一節是禁區，不是建議。
2. **不要合併自己的 PR。** 審查與驗證是兩個關卡，那是廠主的。
3. **不改 `fac-*` 與 `.factory/`。** 要改走外迴圈。
4. **不改 `SPEC.md` 的不變量。** 要改另開任務。
5. **先寫測試，而且每一條要先紅過。** 沒紅過的當成還沒寫。
6. **五條架構規則一條都不能破。** 做不到就停下來回報。
7. **順手修的東西不要塞進來。** 看到別的地方有問題，開一筆新任務。
8. **偏離原計畫寫在 `tasks.md`，不要改 `design.md`。**

第 7 條最常被破。順手修三行會讓審查站多看一個無關的 diff，而風險說明最多 5 點 —— 你佔掉的那一點是別人的。

## 6. 修正訊號

| 廠主改了什麼 | 意思 |
|---|---|
| 在你的 PR 上直接改 code | 看改的是哪一類東西。慣例沒寫進 `tech-spec.md` |
| 退回並說「做太多」 | 範圍界定沒守住。硬規則 1 |
| 退回並說「漏了」 | 「可觀察完成狀態」的自檢放水 |
| 自己補測試 | Testing Strategy 太薄 |

你自己寫的 `_偏離原計畫_` 與「工廠回饋」也是訊號。它們由 `fac-improve-*` 撈。
