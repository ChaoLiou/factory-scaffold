# 外迴圈 — 驗證站

這一份看證據穩不穩，並提案修改 `fac-verify` 或這座工廠的合約宣告。

## 0. 四條共同規則

與 `fac-improve-triage` 第 0 節相同。

## 1. 撈什麼訊號

### 1.0 動作紀錄每週都要讀

修正訊號要等人出手。**動作紀錄不用** —— 它每一輪都產生，而且它記得人沒注意到的那些失敗。

| 從動作紀錄看 | 意思 |
|---|---|
| 同一站反覆重試 | 那一站的判準寫得不清楚 |
| 為了一件小事讀了半個 repo | 脈絡沒指路 |
| 一直在同一個地方停下來回報 | 規則之間打架，或少了一條 |

兩個一起看才完整：修正訊號說「人覺得哪裡不對」，動作紀錄說「工人在哪裡卡住」。見腳手架的 `docs/factory.md` 4.3。


| 訊號 | 在哪看 | 意思 |
|---|---|---|
| A | 容許清單每次都要補同一種區域 | 容許清單的寫法不夠用 |
| B | 兩次連跑一直不一致 | 初始資料不可重現，或並行污染 |
| C | 某一條不變量永遠錄不出畫面 | 那條不變量寫成了願望 |
| D | 合約宣告缺一個欄位 | 宣告的欄位表要加一格 |
| E | 證據貼上去但廠主沒看 | **證據三秒看不懂** |
| F | 上線之後才發現的問題 | 驗證站漏了一條不變量 |
| G | **證據全過，廠主還是退回** | 不變量沒抓到他的品味。判準落差那個指標就是在數這個 |

## 2. 這一站的訊號有兩種去向

別的外迴圈只改 skill。這一份不一樣：

| 訊號 | 要改的東西 | 哪一層 |
|---|---|---|
| A、D | `.factory/contract.json` 的欄位 | 合約宣告。D 要改腳手架 |
| B | `docs/tech-spec.md` 的初始資料 | 專屬 |
| C | `SPEC.md` 的不變量 | **產品決定。要廠主改** |
| E、F | `fac-verify` | 共用。走 PR |
| G | `SPEC.md` 的不變量 | **產品決定。要廠主改**。跟 C 同一個去向 |

**訊號 C 不是你改。** 不變量寫成願望是產品的事，提案給廠主，他決定怎麼改寫。

## 3. 訊號 E 最難看出來

證據貼上去而廠主沒看，不會留下任何痕跡。

要主動問一次：

| 問 | 為什麼 |
|---|---|
| 上一輪的證據你看了嗎 | 沒看就是三秒看不懂 |
| 看了哪幾段 | 只看第一段表示錄影太長 |
| 有沒有哪一段看不出在幹嘛 | 那一段的操作沒錄到過程 |

**「廠主沒看證據」比「證據是錯的」嚴重。** 證據錯了下次會修。沒人看的證據是整座工廠白做。

## 4. 訊號 F 的歸屬

上線之後才發現的問題，先分是哪一種：

| 哪一種 | 屬於 |
|---|---|
| 不變量沒被操作到 | 驗證站。這一份處理 |
| 不變量根本沒寫 | 規格站。交給 `fac-improve-triage` 之外的人處理 |
| 風險說明該標而沒標 | 審查站。交給 `fac-improve-review` |

**不要什麼都算到驗證站頭上。** 它只負責「寫下來的不變量有沒有被操作出來」。

## 5. 提案與留帳

形狀與 `fac-improve-triage` 第 3、4 節相同。

留帳的「層」那一欄要注意：改合約宣告的欄位是**架構層**，改 `fac-verify` 是 skill 層。

**同一個問題能用改欄位解決的時候，不要用改 skill 解決。** 那是往上推一層。

## 6. 硬規則

1. **一次最多兩條。** 那是改動的數量，不是方向 —— **刪掉一條沒有咬到東西的規則，跟加一條新規則一樣是改善。**
2. **沒點頭不准改。**
3. **訊號 C 提案給廠主，不要自己改不變量。**
4. **訊號 E 要主動問，不要等它出現。**
5. **能改欄位就不要改 skill。**
6. **共用檔案走 PR。**
7. **提案要跑重播集。** 改之前跑一次，改之後跑一次。沒有差別的那一條丟掉。見腳手架的 `docs/factory.md` 7.2。
8. **提案要回答「這一條會不會讓某個指標變好而產品沒變好」。** 四個指標都有那條路，見 `docs/factory.md` 8.2。
