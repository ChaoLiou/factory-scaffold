# 建廠產線

這份文件描述腳手架怎麼產生一座工廠。名詞一律照 `../CONTEXT.md`。

產品產線（工廠怎麼產生產品）在 `factory.md`。兩條產線不一樣，不要混。

---

## 1. 建廠不是一個複製指令

原本的設計把建廠當成「複製一份範本」。那是錯的。

建廠有順序性的站、有關卡、有回頭的箭頭、需要證據，而且失敗在哪一站是可以學的訊號。照這個專案自己的定義，那就是一條產線。

所以腳手架自己也是一座工廠，它的產品是工廠。

---

## 2. 七站

| 站 | 做什麼 | 關卡 |
|---|---|---|
| 1 問清產品 | 把廠主的一句話變成白話規格第一版 | **廠主說「這是我要的」** |
| 2 定產品型態 | 問四題需求，查對照表決定技術棧 | **廠主答四題** |
| 3 開 repo | repo、label、分支保護、CI 骨架 | — |
| 4 接合約 | 合約三項要求各自接通，並建立預覽與生產兩個分離的專案 | — |
| 5 寫合約宣告 | 把三項的實際形狀寫成設定 | — |
| 6 驗收 | 對空產品跑一次驗證站 | **廠主看到證據** |
| 7 交付 | 給廠主入口 | — |

回頭的箭頭：

1. 第 6 站驗收不過 → 回第 4 站，修沒通過的那一項。
2. 第 1 站的白話規格被廠主否決 → 留在第 1 站重寫。
3. 第 2 站的四題答完發現型態不對 → 回第 2 站重問。

---

## 3. 驗收標準

**第 6 站的標準只有一條：驗證站跑得出證據。**

工廠在能證明自己會驗證的那一刻才算建好。

這把「產品產線第一站蓋驗證」從偏好變成必要條件。沒有驗證站，建廠就沒有量規，也就無法判斷一座工廠交付得出去。

驗收用的是一個空產品。不需要功能，只需要三項要求成立：預覽打得開、初始資料重置得了、測試帳號登入得進去。

資安的架構規則也要在這一站驗：前端的 build 輸出裡沒有任何憑證，而且預覽專案與生產專案是分開的。

---

## 4. 第二站：問需求，不問技術

廠主不該被問語言、框架或資料庫。他該被問他知道答案的事。

### 4.1 四題

| | 問題 | 選項 |
|---|---|---|
| 1 | 你的東西要怎麼打開？ | 瀏覽器輸入網址 ／ 手機桌面點圖示 ／ 沒有畫面，給別的程式用 ／ 不用人開，自己定時跑 |
| 2 | （答「手機桌面」才問）需要**沒網路也能用**、用**相機或藍牙**、或**出現在 App Store 讓陌生人搜到**嗎？ | 都不需要 ／ 需要其中一項 |
| 3 | 要存每個人各自的資料嗎？ | 要 ／ 不用，大家看到一樣的 |
| 4 | 誰會用？ | 只有我 ／ 我認識的人 ／ 公開給任何人 |

沒有一題提到技術。

- 第 1 題決定產品型態。
- 第 2 題決定 PWA 還是跨平台原生。
- 第 3 題決定合約要求三適不適用。
- 第 4 題決定成本層級。

### 4.2 對照表

| 第 1 題 | 第 2 題 | 產品型態 | 技術棧 |
|---|---|---|---|
| 瀏覽器輸入網址 | — | Web app | Next.js + Supabase |
| 手機桌面點圖示 | 都不需要 | **PWA** | Next.js + Supabase + manifest 與 service worker |
| 手機桌面點圖示 | 需要其中一項 | 跨平台原生 | React Native + Expo |
| 沒有畫面 | — | 後端服務 | Hono + Cloudflare Workers + D1 |
| 自己定時跑 | — | 排程任務 | Cloudflare Workers Cron |

第 3 題答「不用」→ 拿掉 Supabase Auth，合約要求三在那座工廠不適用。

### 4.2.1 三套技術棧都要守同一組架構規則

技術棧可以換，架構規則不能換。見 `security.md` 第 3 節。

最重要的一條：**前端不持有任何可以直接存取資料的憑證。** 所以 Next.js + Supabase 的工廠一律走 server side 查詢，anon key 不進前端，只准 PKCE flow。

代價是沒有 Realtime 訂閱。已經接受。

### 4.2.2 為什麼三套都只有一組規則

**五種產品型態只用三套技術棧。** PWA 就是加了 manifest 與 service worker 的 web app。排程任務與後端服務共用 Workers。這對「一份技能檔服務所有工廠」很重要。

### 4.3 廠主說「我要 APP」時預設給 PWA

| | PWA | 跨平台原生 |
|---|---|---|
| 手機桌面有圖示 | 是 | 是 |
| iOS 與 Android 都能裝 | 是 | 要建兩個包 |
| 要 App Store 審核 | 不要 | 要 |
| 要 macOS | 不要 | iOS 要 |
| 合約三項要改嗎 | **不用改。它還是 web** | 要改 |

民眾說「APP」時，他要的通常是「桌面上有一個圖示，點開就用」。那正是 PWA。

第 2 題三個條件都答「不需要」就走 PWA。絕大多數會落在這裡。

**這台開發機是 WSL2 Linux，沒有 macOS。** 所以 iOS 原生在這裡建置不了，iOS 模擬器也跑不起來，產不出 iOS 原生的證據。Android 模擬器在 Linux 可以跑，`adb screenrecord` 錄得了影。

所以跨平台原生這條路的 iOS 證據要靠雲端裝置。這是走原生的代價之一，要在第 2 題就讓廠主知道。

## 5. 各層級的關卡配置

建廠產線本身也要分層級。L1 民眾不能被要求選技術棧或設 webhook。

| 站 | L1 | L2 | L3 |
|---|---|---|---|
| 1 問清產品 | 關卡 | 關卡 | 關卡 |
| 2 定產品型態 | 關卡（只問四題） | 關卡（四題 + 看結果） | 關卡（四題 + 可覆寫技術棧） |
| 3 開 repo | 全自動 | 全自動 | 可介入 |
| 4 接合約 | 全自動 | 全自動 | 可介入 |
| 5 寫合約宣告 | 全自動 | 全自動 | 可介入 |
| 6 驗收 | 關卡 | 關卡 | 關卡 |
| 7 交付 | 一個連結 | repo + 一個連結 | repo |

三層都只有三個關卡：問清產品、定產品型態、驗收。

這對上 `factory.md` 3.2 那張表的規律：L1 的關卡最少，但永遠包含「這是我要的嗎」與「看證據」。

---

## 6. 腳手架自己的外迴圈

每次建廠卡在哪一站、廠主在哪一關退回，就是修改建廠技能檔的訊號。

所以腳手架需要自己的帳本，記「為什麼這次建廠要人出手」。做法照 `codeshore.md` 4.4 的 `orca-retro` 與 `pacer-log`：一次最多提兩條、沒點頭不准改、零件改動與帳本那一列同一個 commit。

---

## 7. 還沒定的事

1. 第 3 站要用哪個平台開 repo，以及 label 的名稱。
2. 第 4 站「接合約」的三項各自的實際指令。
3. 第 7 站交付給 L1 的那個連結是什麼。聊天管道還沒決定，見 `openclaw.md` 第 6 節。
4. 腳手架的帳本檔名與格式。
5. 四題的答案要存在哪裡。它是白話規格的一部分，還是另一份設定。
6. 廠主的帳號安全要不要變成建廠產線的一站。見 `security.md` 第 6 節第 3 項。
