# 建廠產線

這份文件描述腳手架怎麼產生一座工廠。名詞一律照 `../CONTEXT.md`。

產品產線（工廠怎麼產生產品）在 `factory.md`。兩條產線不一樣，不要混。

---

## 1. 建廠不是一個複製指令

原本的設計把建廠當成「複製一份範本」。那是錯的。

建廠有順序性的站、有關卡、有回頭的箭頭、需要證據，而且失敗在哪一站是可以學的訊號。照這個專案自己的定義，那就是一條產線。

所以腳手架自己也是一座工廠，它的產品是工廠。

---

## 2. 六站

| 站 | 做什麼 | 關卡 |
|---|---|---|
| 1 定產品型態 | 問一句話加五題，查對照表決定產品型態 | **廠主答五題** |
| 2 開 repo | repo、標籤、分支保護、CI 骨架 | — |
| 3 接合約 | 合約三項要求各自接通，並建立預覽與生產兩個分離的專案 | — |
| 4 寫合約宣告 | 把三項的實際形狀寫成設定 | — |
| 5 驗收 | 對空產品跑一次驗證站 | **廠主看到證據** |
| 6 交付 | 給廠主入口 | — |

回頭的箭頭：

1. 第 5 站驗收不過 → 回第 3 站，修沒通過的那一項。
2. 第 1 站的五題答完發現型態不對 → 留在第 1 站重問。

**兩個關卡。** 兩個都問工廠，不問產品。

---

## 2.1 建廠不問產品規格

這一條以前不是這樣。原本的第 1 站叫「問清產品」，產出是白話規格第一版，關卡是廠主說「這是我要的」。

**那一站拿掉了。** 三個理由。

### 2.1.1 沒有一站需要它

| 站 | 需要白話規格嗎 |
|---|---|
| 1 定產品型態 | 不要。它只要一句話與五題的答案 |
| 2 開 repo | 不要 |
| 3 接合約 | 不要 |
| 4 寫合約宣告 | 不要 |
| 5 驗收 | **不要。它用一個空產品** |
| 6 交付 | 不要 |

驗收用的是空產品。不需要功能，只需要三項要求成立。見第 3 節。

**所以建廠產線從頭到尾不讀白話規格。** 它產出一份沒人讀的文件。

### 2.1.2 規格站比它會做這件事

那一站的工作是「把廠主要的東西寫成規格，並讓他點頭」。

產品產線的規格站就是做這件事的，而且做得完整得多：

| | 建廠產線的第 1 站（已拿掉） | 規格站 |
|---|---|---|
| 核准 | 一道 | 三道：需求、設計、任務 |
| 驗收條件 | 沒有固定句型 | EARS 三種句型 |
| 範圍界定 | 沒有 | 有，而且要寫理由 |
| 需求對到設計 | 沒有 | Requirements Traceability |

**把它留在建廠產線，等於要蓋第二套規格機制。** 而那一套比較差。

### 2.1.3 時序上它也不該在這裡

建廠的時候工廠還不存在。所以那個關卡沒有東西可以執行它 —— 沒有入口站、沒有規格站、沒有工人。

**白話規格是工廠建好之後第一筆任務的事。**

那筆任務走完整的產品產線：入口 → 分辨（判成複雜）→ 規格（三道核准）→ 實作 → 審查 → 驗證 → 上線。

「這是我要的嗎」那一關沒有消失。它搬到規格站，而那裡是它本來該在的位置。

### 2.1.4 建廠只填 `SPEC.md` 的兩節

| `SPEC.md` 的節 | 誰填 |
|---|---|
| 定位（一句話） | **建廠第 1 站** |
| 建廠的五題答案 | **建廠第 1 站** |
| 目標使用者 | 第一筆任務 |
| 核心能力 | 第一筆任務 |
| 不變量 | 第一筆任務 |
| 不做的事 | 第一筆任務 |

那一句話是建廠要的最小輸入。它用來命名 repo 與工廠，而且第 1 題的答案要靠它才問得出來。

**不變量留空是對的。** 它是驗證站的判準來源，而驗收跑的是空產品 —— 空產品沒有不變量可以驗。

## 2.2 這條線不只跑第一次

上面那六站是**第一次**建廠。建廠產線還有兩站，都在工廠建好之後才跑：**工廠升級**與**拆廠**。規格見 `skills-layering.md` 第 6 節。

| | 跑幾次 | 改的是 |
|---|---|---|
| 六站 | 一次 | 從沒有到有 |
| 工廠升級 | **腳手架每出一版就一次** | 共用那一半的 skill |
| 拆廠 | 一次，最後一次 | 清掉這座工廠 |

**工廠自己也要迭代，不然它停在交付那天的水準。** 迭代有兩條路，而它們不一樣：

| | 誰改 | 影響 |
|---|---|---|
| 外迴圈 | 這座工廠改它自己的 skill | 只有這一座 |
| 工廠升級 | 腳手架改共用層，升級站換進來 | 每一座 |

這跟產品一版一版變好是第三件事。產品走產品產線，工廠走這兩條。

### 2.2.1 向下那條路現在是斷的

向上的路已經有了：工廠的外迴圈改到共用 skill，就對腳手架送一個 PR。見 `skills-layering.md` 第 5 節。

**向下的路還沒蓋。** 腳手架合併了那個 PR 之後，沒有一站把新版的共用層換進已經存在的工廠。

所以跨工廠學習現在只有一半。這不是「以後再補的功能」—— 少了它，一座工廠就只能靠自己的外迴圈進步。

### 2.2.2 升級可以動什麼，不能動什麼

升級是自動的，而且它動到每一座工廠。所以分類的判準只有一條：**改錯之後廠主會不會發現。**

| 類 | 誰可以改 | 升級時 |
|---|---|---|
| **共用層** | 只有腳手架 | 整批換掉 |
| **專屬層** | 只有這座工廠 | 不碰 |
| **死守** | 沒有人 | 不碰，而且要檢查它還在 |
| **歷史** | 只能新增 | 不碰，不重寫 |

逐項歸類：

| 檔案或設定 | 類 | 升級時 |
|---|---|---|
| `.claude/skills/fac-*` | 共用 | 整批換 |
| `.factory/security.md` | 共用 | 整批換 |
| `CLAUDE.md` 與 `CONTEXT.md` 的 `fac:shared` 區 | 共用 | 只換那一區 |
| CI 要擋的那四項 | 共用 | 整批換 |
| `.claude/skills/` 底下無前綴的 | 專屬 | 不碰 |
| `SPEC.md` | 專屬 | 不碰 |
| `docs/tech-spec.md` | 專屬 | 不碰 |
| `.factory/contract.json` 的值 | 專屬 | 不碰 |
| `.factory/checks.json` 的指令 | 專屬 | 不碰 |
| 標籤名稱 | **死守** | 只能加。不能改名，不能刪 |
| 三個關卡 | **死守** | 只能加，不能減 |
| 五條架構層資安規則 | **死守** | 只能加嚴 |
| 產品合約三項要求 | **死守** | 不能減，也不能加第四項 |
| `manifest.json` 的 `product_form` | **死守** | 不碰 |
| `docs/factory-log.md` | 歷史 | 只能 append |
| `specs/<feature>/` | 歷史 | 不重寫 |
| `.factory/evidence/` | 歷史 | 不重寫 |

### 2.2.3 死守那一類為什麼最危險

把判準套上去，就看得出哪一項最嚴重：

| 升級改錯了 | 廠主會發現嗎 |
|---|---|
| 共用 skill 寫壞 | 會。產出變差，或驗證站跑不出證據 |
| 標籤改名 | 會。任務卡住不動 |
| **關卡被拿掉** | **不會。沒有人被叫，所以沒有人知道自己該被叫** |
| 架構層資安規則被放寬 | 不會。資料外洩不出現在錄影裡 |

**最後兩列是同一個形狀：少了的東西不會叫。** 這跟 `security.md` 第 2 節把資安往架構層推的理由完全一樣。

所以關卡與架構規則不交給升級站判斷。它們是升級要**檢查還在不在**的東西，不是升級可以換的東西。

### 2.2.4 雜湊只守一個方向

`manifest.json` 的雜湊比對守的是「工廠本地改了共用層」。那是工廠改腳手架的方向。

**反方向沒有守。** 升級站是腳手架在改工廠，雜湊比對擋不住它。所以死守那一類要靠另外三道：

1. **CI 檢查。** 標籤清單、三個關卡、五條架構規則都還在。
2. **升級的驗收。** 跑一次驗證站，與建廠第 5 站同一條標準。
3. **廠主確認。** 有雜湊不符時一定要人看。見 `skills-layering.md` 6.1。

第 1 道現在還沒有。`.factory/checks.json` 的格式還沒定，見 `security.md` 4.2。

## 3. 驗收標準

**第 5 站的標準只有一條：驗證站跑得出證據。**

工廠在能證明自己會驗證的那一刻才算建好。

這把「產品產線第一站蓋驗證」從偏好變成必要條件。沒有驗證站，建廠就沒有量規，也就無法判斷一座工廠交付得出去。

驗收用的是一個空產品。不需要功能，只需要三項要求成立：預覽打得開、初始資料重置得了、測試帳號登入得進去。

資安的架構規則也要在這一站驗：前端的 build 輸出裡沒有任何憑證，而且預覽專案與生產專案是分開的。

---

## 4. 第一站：問需求，不問技術

廠主不該被問語言、框架或資料庫。他該被問他知道答案的事。

### 4.1 五題

| | 問題 | 選項 |
|---|---|---|
| 1 | 你的東西要怎麼打開？ | 瀏覽器輸入網址 ／ 手機桌面點圖示 ／ 沒有畫面，給別的程式用 ／ 不用人開，自己定時跑 |
| 2 | （答「手機桌面」才問）需要**沒網路也能用**、用**相機或藍牙**、或**出現在 App Store 讓陌生人搜到**嗎？ | 都不需要 ／ 需要其中一項 |
| 3 | 要存每個人各自的資料嗎？ | 要 ／ 不用，大家看到一樣的 |
| 4 | 誰會用？ | 只有我 ／ 我認識的人 ／ 公開給任何人 |
| 5 | 它會存**別人**的資料嗎？例如客戶的姓名、電話、訂單 | 不會，只有我自己的 ／ 會 |

沒有一題提到技術。

- 第 1 題決定產品型態。
- 第 2 題決定 PWA 還是跨平台原生。
- 第 3 題決定合約要求三適不適用。
- 第 4 題決定成本層級。
- 第 5 題決定要不要啟用個資規則。見 4.4。

### 4.2 對照表

對照表查出來的是**產品型態**，不是技術棧。

| 第 1 題 | 第 2 題 | 產品型態 | 預覽是什麼 | 證據是什麼 |
|---|---|---|---|---|
| 瀏覽器輸入網址 | — | Web app | 一個 HTTPS 網址 | 錄影 + 截圖 |
| 手機桌面點圖示 | 都不需要 | **PWA** | 一個 HTTPS 網址 | 錄影 + 截圖，多一段裝到桌面 |
| 手機桌面點圖示 | 需要其中一項 | 跨平台原生 | 一個裝得進模擬器或裝置的建置 | 模擬器錄影 |
| 沒有畫面 | — | 後端服務 | 一個 HTTPS endpoint | 請求與回應的對照表 |
| 自己定時跑 | — | 排程任務 | 一個手動觸發的入口 | 輸入輸出對照 + 日誌 |

這張表沒有一格是產品技術。它三欄都是產品的事實：怎麼打開、拿什麼給證據產生器操作、廠主看到什麼。

第 3 題答「不用」→ 合約要求三在那座工廠不適用，`contract.json` 的 `login.applicable` 填 `false`。

### 4.2.1 起始技術棧是預設值，不是決定

**腳手架不決定產品技術。** 見 `factory.md` 2.1。

但第 5 站的驗收要對一個空產品跑一次驗證站。空產品要有預覽，預覽要有東西可以部署。所以第 2 站必然要產出一個跑得起來的東西，而那必然用了某一套技術棧。

這兩件事的解法是改定位，不是改有沒有：

| | 產品型態 | 起始技術棧 |
|---|---|---|
| 誰定 | 五題。對照表查出來 | 第 2 站挑一個預設值 |
| 可以換嗎 | 不行。換型態等於換產品 | **可以。一筆任務** |
| 寫在哪 | `SPEC.md` 與 `manifest.json` | `docs/tech-spec.md` |
| 共用 skill 知道嗎 | 知道。它決定證據的形式 | **不知道。它只讀合約宣告** |

預設值清單不寫在這份文件裡，因為它會變，而這份文件定的是不變的部分。它跟著 `template/` 走。

換技術棧要改哪些檔案，見 `product-contract.md` 第 8 節。

### 4.2.2 架構層規則不隨技術棧變

技術棧可以換，架構層規則不能換。見 `security.md` 第 3 節。

最重要的一條：**前端不持有任何可以直接存取資料的憑證。**

它限制架構，不限制產品技術 —— 任何技術棧都做得到「資料查詢一律走 server、只准 PKCE flow、session 寫成 HttpOnly cookie」。

代價是沒有即時訂閱，前提是那個訂閱機制需要前端持有 token。已經接受。

### 4.2.3 產品型態少，但不是因為技術棧少

五種產品型態只有三種預覽形式：一個網址、一個建置、一個觸發入口。

**這才是「一份 skill 服務所有工廠」依賴的東西。** 它依賴預覽與證據的形式數量少，不依賴技術棧數量少。

原本這一段寫的是「五種型態只用三套技術棧，這對一份 skill 很重要」。那句話站不住：共用 skill 讀合約宣告，不讀技術棧。技術棧多寡與 skill 的改善速度無關。

### 4.2.4 部署平台也是起始值

同一個道理再套一次。**腳手架不挑平台。**

它定的是預覽機制要滿足的五條，見 `factory.md` 2.1。平台是滿足那五條的實作。

| | 五條要求 | 哪一家平台 |
|---|---|---|
| 誰定 | 腳手架。定死 | 第 3 站挑一個起始值 |
| 可以換嗎 | 不行 | **可以。一筆任務** |
| 寫在哪 | `security.md` 與合約要求一 | `docs/tech-spec.md` 的「部署」那一節 |
| 共用 skill 知道嗎 | 知道 | **不知道。它只讀合約宣告的 `preview` 欄位** |

起始平台的清單不寫進這份文件，理由跟起始技術棧一樣：它會變，而這份文件定的是不變的部分。

#### 4.2.4.1 挑平台的時候只問那五條

不要比功能表。照順序問五個是或不是：

1. 每個 PR 自動給一個預覽嗎？
2. 那個位置猜不到嗎？
3. 機器帶一個 token 進得去嗎？
4. 預覽與生產分得開成兩個專案、兩個帳號嗎？
5. 密鑰由它注入，而工人讀不到嗎？

**五條有一條做不到，那個平台就不符合合約。** 這比「哪一家比較好」好回答得多，而且它不會隨著平台改版過期。

### 4.3 廠主說「我要 APP」時預設給 PWA

| | PWA | 跨平台原生 |
|---|---|---|
| 手機桌面有圖示 | 是 | 是 |
| iOS 與 Android 都能裝 | 是 | 要建兩個包 |
| 要 App Store 審核 | 不要 | 要 |
| 要 macOS | 不要 | iOS 要 |
| 合約三項要改嗎 | **不用改。它還是 web** | 要改 |

民眾說「APP」時，他要的通常是「桌面上有一個圖示，點開就用」。那正是 PWA。

第 2 題三個條件都答「不需要」就走 PWA。絕大多數會落在這裡。

**這台開發機是 WSL2 Linux，沒有 macOS。** 所以 iOS 原生在這裡建置不了，iOS 模擬器也跑不起來，產不出 iOS 原生的證據。Android 模擬器在 Linux 可以跑，`adb screenrecord` 錄得了影。

所以跨平台原生這條路的 iOS 證據要靠雲端裝置。這是走原生的代價之一，要在第 2 題就讓廠主知道。

## 4.4 第五題答「會」啟用的規則

第 5 題答「不會，只有我自己的」→ 這一節整組不適用。洩漏的後果只影響廠主本人。

答「會」→ 產品存了第三人的資料，廠主要對那些人負責。啟用下面這組規則。

照 `security.md` 第 2 節的排序，能往上推的就往上推。

### 4.4.1 架構層

| 規則 | 擋什麼 |
|---|---|
| **禁止產品自己處理卡號。** 付款一律走第三方的託管頁面 | 卡號根本不進產品，PCI 的範圍整個消失 |
| **禁止存身分證號與完整金融帳號** | 不存的東西不會洩漏 |
| **禁止存密碼。** 認證一律交給託管的認證服務 | 自己做密碼雜湊是高風險 |

這三條都是「不存就不會洩漏」。它們是架構層，因為做不到就是真的做不到。

### 4.4.2 CI 層

| 檢查 | 擋什麼 |
|---|---|
| 掃 migration 有沒有新增像個資的欄位名 | 悄悄多出一欄身分證號 |
| 每張存別人資料的表必須有保留期限欄位 | 資料無限期堆積 |

### 4.4.3 rules 層

1. **資料最小化。** 只存產品功能真的需要的欄位。少一欄就少一分風險。
2. **保留期限。** 每張存別人資料的表要有期限，過期自動刪。
3. **刪除權。** 終端使用者要能刪掉自己的資料。

### 4.4.4 多一個關卡

產品產線的規格站新增一張「存別人資料」的表時，要廠主看一眼並確認。

這一條放在規格站，不放在實作站。理由是決定「要不要存這個欄位」是產品決定，不是實作決定。

### 4.4.5 還沒解的事

**責任歸屬。** 一座工廠讓民眾三句話做出一個收集客戶電話的網站，那個責任是誰的。

這題在廠主不是你的時候才咬人。見 `security.md` 第 6 節。

## 5. 各層級的關卡配置

建廠產線本身也要分層級。L1 民眾不能被要求選技術棧或設 webhook。

**現在只實作 L3。** L1 與 L2 那兩欄是設計保留。見 `../CLAUDE.md` 的「範圍」。

| 站 | L1（未開放） | L2（未開放） | **L3（進行中）** |
|---|---|---|---|
| 1 定產品型態 | 關卡（只問五題） | 關卡（五題 + 看查出來的型態） | **關卡（五題 + 可換起始技術棧）** |
| 2 開 repo | 全自動 | 全自動 | **可介入** |
| 3 接合約 | 全自動 | 全自動 | **可介入** |
| 4 寫合約宣告 | 全自動 | 全自動 | **可介入** |
| 5 驗收 | 關卡 | 關卡 | **關卡** |
| 6 交付 | 一個連結 | repo + 一個連結 | **repo** |

三層都只有兩個關卡：定產品型態、驗收。

**「這是我要的嗎」那一關不在這條線上。** 它在工廠建好之後第一筆任務的規格站。見 2.1.3。

這一點對 L1 特別重要。`factory.md` 3.2 說 L1 的關卡「永遠包含『這是我要的嗎』與『看證據』」—— 那句話講的是產品產線。建廠產線只有「看證據」那一半。

## 6. 腳手架自己的外迴圈

每次建廠卡在哪一站、廠主在哪一關退回，就是修改建廠 skill 的訊號。

所以腳手架需要自己的帳本，記「為什麼這次建廠要人出手」。規則與工廠的外迴圈相同：一次最多提兩條、沒點頭不准改、零件改動與帳本那一列同一個 commit。

**這條外迴圈不是廠主的事。** 它住在腳手架 repo，訊號也只有腳手架看得到 —— 一個廠主一輩子建一次廠，手上只有一個樣本，改不動這條線。

廠主那邊只剩兩件跟腳手架有關的事：

1. 升級站那個關卡 —— 要不要換新版的共用層。
2. 他的外迴圈改到共用層的時候，送一個 PR 上來。見 `skills-layering.md` 第 5 節。
