# 產品合約

這份文件定義產品合約。名詞一律照 `../CONTEXT.md`。

技術棧的對照表在 `factory-setup.md` 4.2。這份文件定的是「skill 依賴什麼」，所以它比對照表更根本：對照表可以換，合約不該換。

---

## 1. 為什麼要有合約

驗證站要用一份 skill 服務所有工廠。一份要處理三種技術棧的 skill，改善速度是三分之一。

合約的用途是讓那一份 skill 有固定的東西可以依賴，而不是讓技術棧只剩一套。

合約有三項要求。三項都是驗證站要的。

---

## 2. 要求一：每個 PR 一個可以被操作的預覽

### 2.1 內容

| | 條件 |
|---|---|
| 必須 | 每個 PR 自動產生一個可以被操作的預覽 |
| 必須 | PR 推新 commit 之後，預覽指向新版本 |
| 必須 | 預覽的壽命至少七天 |
| 必須 | 證據產生器打得開它，不需要人介入 |
| 必須 | 位置**不可猜測**。`pr-123.example.com` 不行 |
| 必須 | 用 service token 擋陌生人。工人帶 token，人不帶 |

### 2.2 預覽長什麼樣，隨產品型態變

| 產品型態 | 預覽是什麼 |
|---|---|
| Web app | 一個 HTTPS 網址 |
| PWA | 一個 HTTPS 網址。與 Web app 相同 |
| 跨平台原生 | 一個裝得進模擬器或裝置的建置 |
| 後端服務 | 一個 HTTPS endpoint |
| 排程任務 | 一個可以手動觸發一次的執行入口 |

原本這一項寫死成「預覽網址」。那是 web 專屬的假設，原生 APP 與排程任務都沒有網址。

### 2.3 理由

沒有預覽，證據產生器無從操作產品。

七天這個數字來自關卡：廠主可能隔幾天才看證據。預覽在他看之前就失效，證據等於沒有。

### 2.4 怎麼檢查

工廠從 PR 讀得到預覽的位置，而且證據產生器打得開它。

---

## 3. 要求二：一組可重現的初始資料

### 3.1 內容

| | 條件 |
|---|---|
| 必須 | 一個指令就能把產品回到已知狀態 |
| 必須 | 同一個 commit 跑兩次，證據的畫面一致 |
| 必須 | 初始資料存在版本控制裡 |
| 必須 | 初始資料是**合成的**。絕不從生產環境複製 |
| 必須 | 預覽與生產是**不同的專案、不同的帳號**，不是兩組環境變數 |

### 3.2 理由

這一項最難。

沒有可重現的初始資料，每次錄影的畫面都不一樣。廠主看兩段影片，分不出差別是這次改動造成的，還是資料不同造成的。那證據就不是證據。

### 3.3 第一版的做法與它的缺陷

**決定：所有預覽共用一個資料庫，每輪跑證據之前重置。**

| 方案 | 成本 | 為什麼沒選 |
|---|---|---|
| **共用一個，每輪重置** | 免費 | **選這個** |
| 資料庫層的分支功能 | 付費方案起跳 | 民眾工廠付不起 |
| 資料庫層的分支功能，另一家 | 免費方案含分支 | 沒有認證與檔案儲存，工廠基礎設施變兩家廠商 |
| 每個預覽一個 schema | 免費 | 託管認證服務的帳號表不好分 schema，登入會隣居 |

**已知缺陷：並行的 PR 會互相污染。** 兩個 PR 同時跑證據，後重置的那個會打掉前一個的畫面。

接受這個缺陷的理由是第一座工廠只有一個廠主，並行很少發生。廠主變多、或同時跑的 PR 變多的時候，這一項要重新決定。

原本寫的「每個預覽網址有自己的資料，不與其他預覽網址共用」這條要求先拿掉。它是對的，但現在付不起。

### 3.4 怎麼檢查

連跑兩次證據產生器，證據逐像素比對。

畫面上本來就會變的區域（時間、動畫、隨機排序）列進容許清單。容許清單寫在工廠的設定裡，不寫在 skill 裡 — 每個產品的動態區域不一樣。

## 4. 要求三：一個固定的登入方式

### 4.1 適用範圍

這一項只在產品要存每個人各自的資料時適用。見 `factory-setup.md` 4.1 的第 3 題。

答「不用，大家看到一樣的」的工廠，這一項不適用。

### 4.2 內容

| | 條件 |
|---|---|
| 必須 | 一組測試帳號，由初始資料建立 |
| 必須 | 登入步驟固定，而且不需要人 |
| 必須 | 產品有角色之分時，每個角色一組帳號 |
| 禁止 | 簡訊驗證碼 |
| 禁止 | captcha |
| 禁止 | 跳轉到第三方的 OAuth |
| 必須 | 測試帳號的登入方式**只開在預覽專案**，生產專案關掉 |

### 4.3 理由

產品有登入時，沒有測試帳號，證據產生器只錄得到首頁。

三條禁止項都是同一個原因：它們需要人介入，而驗證站上面沒有人。

產品自己可以有簡訊驗證或 Google 登入。合約要求的是**另外**有一條給工人走的固定路徑。

### 4.4 測試帳號不是後門

因為預覽與生產是不同專案（見 3.3 與 `security.md` 3.2），測試帳號物理上不存在於生產環境。

| | 預覽專案 | 生產專案 |
|---|---|---|
| email + password | **開**，給工人用 | **關** |
| 第三方 OAuth | 關 | 開 |

### 4.5 怎麼檢查

證據產生器用 skill 裡寫死的步驟登入，然後抓到一個只有登入後才看得到的畫面。

## 5. 證據的形式隨產品型態變

「廠主三秒看懂」這條標準不變，但媒介變了。

| 產品型態 | 證據是什麼 |
|---|---|
| Web app ／ PWA | 瀏覽器操作錄影 + 截圖 |
| 跨平台原生 | 模擬器或裝置的操作錄影 |
| 後端服務 | 請求與回應的對照表。**沒有畫面可以錄** |
| 排程任務 | 輸入與輸出的對照 + 執行日誌 |

後端服務與排程任務這兩種，3.4 的逐像素比對不適用。它們的可重現性要比對結構化輸出，不比對畫面。

---

## 6. 合約不管的事

合約刻意不限制這些：

- 程式語言
- 前端框架
- 資料庫
- CSS 方案
- 目錄結構
- 測試框架

工廠不管產品怎麼寫。工廠只管產品能不能被驗證、能不能上線、能不能被監控。

這條界線要守住。合約每多一項，技術棧的選擇就少一批，而工廠換不到任何東西。

**唯一的例外是資安的架構規則。** 它們限制架構，不限制技術棧 —— 任何技術棧都做得到「前端不持有憑證」。見 `security.md` 第 3 節。

---

## 7. 合約宣告

產品用一份合約宣告告訴工廠「我這三項長什麼樣」。

工廠讀合約宣告，不猜。這樣同一份 skill 服務得了不同技術棧。

合約宣告要宣告的東西：

1. 產品型態
2. 預覽的位置從 PR 的哪裡讀
3. 重置初始資料的指令
4. 每組測試帳號的身分與登入步驟，或宣告「不適用」
5. 動態區域的容許清單

### 7.1 檔案與格式

`.factory/contract.json`。範本在 `../template/.factory/contract.json`。

格式等到證據產生器寫出第一版才定，因為欄位需求要由它決定。`fac-verify` 寫出來了，所以這一節現在定得出來。

### 7.2 欄位

| 欄位 | 誰讀它 | 內容 |
|---|---|---|
| `contract_version` | 升級 | 合約的版本。現在是 `1` |
| `product_form` | `fac-verify` 第 4 節 | `web`、`pwa`、`native`、`service`、`cron` 之一 |
| `preview.read_from` | 3.1 | 預覽的位置從 PR 的哪裡讀 |
| `preview.match` | 3.1 | 同一個 PR 有多個部署時，認哪一個 |
| `preview.commit_check` | 3.2 | 怎麼確認預覽指向哪一個 commit |
| `preview.service_token_env` | 3.1 | 帶哪些環境變數進去。**存名字，不存值** |
| `preview.ready_timeout_seconds` | 3.2 | 等預覽指向新版本，等多久 |
| `seed.reset_command` | 3.3 | 把產品回到已知狀態的那個指令 |
| `seed.ready_check` | 3.3 | 怎麼確認重置做完了 |
| `login.applicable` | 3.5 | 第 3 題答「不用」的工廠填 `false` |
| `login.accounts[].role` | 3.5 | 這組測試帳號是哪個角色 |
| `login.accounts[].email_env` | 3.5 | 帳號存在哪個環境變數。**存名字，不存值** |
| `login.accounts[].password_env` | 3.5 | 密碼存在哪個環境變數。**存名字，不存值** |
| `login.accounts[].login_path` | 3.5 | 登入從哪裡進去 |
| `login.accounts[].signed_in_marker` | 3.5 | 只有登入後才看得到的那個東西 |
| `allowance[].kind` | 第 5 節 | `selector` 或 `field` |
| `allowance[].value` | 第 5 節 | 要跳過的那個區域或欄位 |
| `allowance[].why` | 第 5 節 | 為什麼它會變。時間、動畫、隨機排序 |

### 7.3 三件不要加進去的事

1. **憑證的值。** 合約宣告在版本控制裡，所以它只存環境變數的名字。
2. **要操作哪些不變量。** 那由 `SPEC.md` 與 PR 的 diff 決定，見 `fac-verify` 3.4。
3. **第四項要求。** 合約每多一項，技術棧的選擇就少一批，而工廠換不到任何東西。

### 7.4 容許清單怎麼寫

`kind` 分兩種，因為有畫面的三種產品型態與沒有畫面的兩種跳過的東西不一樣。

| `kind` | 用在 | `value` 是什麼 |
|---|---|---|
| `selector` | `web`、`pwa`、`native` | 畫面上那塊區域 |
| `field` | `service`、`cron` | 回應裡那個欄位 |

容許清單寫在這裡，不寫在 skill 裡。每個產品的動態區域不一樣。

`why` 是必填的。沒有理由的那一條，下次沒有人敢刪。

## 8. 換技術棧要改哪些檔案

技術棧是起始值，不是決定。見 `factory.md` 2.1 與 `factory-setup.md` 4.2.1。

換它是產品產線的一筆任務，不是重新建廠。

| 檔案 | 要改嗎 |
|---|---|
| `docs/tech-spec.md` | **改。**它就是寫產品技術的那一份 |
| `.factory/contract.json` | **改。**三項要求的實際形狀會變 |
| `.factory/checks.json` | **改。**CI 那四項的指令會變。見 `security.md` 4.2 |
| `SPEC.md` | 不改。白話規格與技術無關 |
| `SPEC.md` 的不變量 | 不改。換技術棧不該換掉產品的性質 |
| `.claude/skills/fac-*` | **不改。**它們讀合約宣告，不讀技術棧 |
| `manifest.json` 的 `product_form` | 不改。換技術棧不是換產品型態 |

**最後兩列是這整件事的量規。** 哪一天換技術棧要動到 `fac-*`，那就是共用層漏了技術棧進去。

那時要修的是共用層，不是這次換棧。

---

## 9. 還沒定的事

1. 要求二的並行污染什麼時候要重新決定。見 3.3。

第 7 節原本還欠三項：檔案格式、容許清單的寫法、沒有畫面的那兩種怎麼比對可重現性。`fac-verify` 第一版寫出來之後它們定了，見 7.2、7.4 與 `fac-verify` 5.2。

它們定在第一次真的跑之前，所以第一次跑完要回頭看一次。
