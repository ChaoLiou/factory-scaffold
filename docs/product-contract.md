# 產品合約

這份文件定義產品合約。名詞一律照 `../CONTEXT.md`。

技術棧的對照表在 `factory-setup.md` 4.2。這份文件定的是「技能檔依賴什麼」，所以它比對照表更根本：對照表可以換，合約不該換。

---

## 1. 為什麼要有合約

驗證站要用一份技能檔服務所有工廠。一份要處理三種技術棧的技能檔，改善速度是三分之一。

合約的用途是讓那一份技能檔有固定的東西可以依賴，而不是讓技術棧只剩一套。

合約有三項要求。三項都是驗證站要的。

---

## 2. 要求一：每個 PR 一個可以被操作的預覽

### 2.1 內容

| | 條件 |
|---|---|
| 必須 | 每個 PR 自動產生一個可以被操作的預覽 |
| 必須 | PR 推新 commit 之後，預覽指向新版本 |
| 必須 | 預覽的壽命至少七天 |
| 必須 | 證據產生器打得開它，不需要人介入 |

### 2.2 預覽長什麼樣，隨產品型態變

| 產品型態 | 預覽是什麼 |
|---|---|
| Web app | 一個 HTTPS 網址 |
| PWA | 一個 HTTPS 網址。與 Web app 相同 |
| 跨平台原生 | 一個裝得進模擬器或裝置的建置 |
| 後端服務 | 一個 HTTPS endpoint |
| 排程任務 | 一個可以手動觸發一次的執行入口 |

原本這一項寫死成「預覽網址」。那是 web 專屬的假設，原生 APP 與排程任務都沒有網址。

### 2.3 理由

沒有預覽，證據產生器無從操作產品。

七天這個數字來自關卡：廠主可能隔幾天才看證據。預覽在他看之前就失效，證據等於沒有。

### 2.4 怎麼檢查

工廠從 PR 讀得到預覽的位置，而且證據產生器打得開它。

---

## 3. 要求二：一組可重現的初始資料

### 3.1 內容

| | 條件 |
|---|---|
| 必須 | 一個指令就能把產品回到已知狀態 |
| 必須 | 同一個 commit 跑兩次，證據的畫面一致 |
| 必須 | 初始資料存在版本控制裡 |

### 3.2 理由

這一項最難。

沒有可重現的初始資料，每次錄影的畫面都不一樣。廠主看兩段影片，分不出差別是這次改動造成的，還是資料不同造成的。那證據就不是證據。

### 3.3 第一版的做法與它的缺陷

**決定：所有預覽共用一個資料庫，每輪跑證據之前重置。**

| 方案 | 成本 | 為什麼沒選 |
|---|---|---|
| **共用一個，每輪重置** | 免費 | **選這個** |
| Supabase branching | 付費方案起跳 | 民眾工廠付不起 |
| Neon Postgres branching | 免費方案含分支 | 沒有 Auth 與 Storage，技術棧變兩家廠商 |
| 每個預覽一個 schema | 免費 | Supabase Auth 的使用者表不好分 schema，登入會隣居 |

**已知缺陷：並行的 PR 會互相污染。** 兩個 PR 同時跑證據，後重置的那個會打掉前一個的畫面。

接受這個缺陷的理由是第一座工廠只有一個廠主，並行很少發生。廠主變多、或同時跑的 PR 變多的時候，這一項要重新決定。

原本寫的「每個預覽網址有自己的資料，不與其他預覽網址共用」這條要求先拿掉。它是對的，但現在付不起。

### 3.4 怎麼檢查

連跑兩次證據產生器，證據逐像素比對。

畫面上本來就會變的區域（時間、動畫、隨機排序）列進容許清單。容許清單寫在工廠的設定裡，不寫在技能檔裡 — 每個產品的動態區域不一樣。

---

## 4. 要求三：一個固定的登入方式

### 4.1 適用範圍

這一項只在產品要存每個人各自的資料時適用。見 `factory-setup.md` 4.1 的第 3 題。

答「不用，大家看到一樣的」的工廠，這一項不適用。

### 4.2 內容

| | 條件 |
|---|---|
| 必須 | 一組測試帳號，由初始資料建立 |
| 必須 | 登入步驟固定，而且不需要人 |
| 必須 | 產品有角色之分時，每個角色一組帳號 |
| 禁止 | 簡訊驗證碼 |
| 禁止 | captcha |
| 禁止 | 跳轉到第三方的 OAuth |

### 4.3 理由

產品有登入時，沒有測試帳號，證據產生器只錄得到首頁。

三條禁止項都是同一個原因：它們需要人介入，而驗證站上面沒有人。

產品自己可以有簡訊驗證或 Google 登入。合約要求的是**另外**有一條給 agent 走的固定路徑。

### 4.4 怎麼檢查

證據產生器用技能檔裡寫死的步驟登入，然後抓到一個只有登入後才看得到的畫面。

---

## 5. 證據的形式隨產品型態變

「廠主三秒看懂」這條標準不變，但媒介變了。

| 產品型態 | 證據是什麼 |
|---|---|
| Web app ／ PWA | 瀏覽器操作錄影 + 截圖 |
| 跨平台原生 | 模擬器或裝置的操作錄影 |
| 後端服務 | 請求與回應的對照表。**沒有畫面可以錄** |
| 排程任務 | 輸入與輸出的對照 + 執行日誌 |

後端服務與排程任務這兩種，3.4 的逐像素比對不適用。它們的可重現性要比對結構化輸出，不比對畫面。

---

## 6. 合約不管的事

合約刻意不限制這些：

- 程式語言
- 前端框架
- 資料庫
- CSS 方案
- 目錄結構
- 測試框架

工廠不管產品怎麼寫。工廠只管產品能不能被驗證、能不能上線、能不能被監控。

這條界線要守住。合約每多一項，技術棧的選擇就少一批，而工廠換不到任何東西。

---

## 7. 合約宣告

產品用一份合約宣告告訴工廠「我這三項長什麼樣」。

工廠讀合約宣告，不猜。這樣同一份技能檔服務得了不同技術棧。

合約宣告要宣告的東西：

1. 產品型態
2. 預覽的位置從 PR 的哪裡讀
3. 重置初始資料的指令
4. 每組測試帳號的身分與登入步驟，或宣告「不適用」
5. 動態區域的容許清單

檔案格式與欄位名稱還沒定。等證據產生器寫出第一版，欄位需求才會準。先定需求，不先定格式。

---

## 8. 還沒定的事

1. 合約宣告的檔案格式與欄位名稱。見第 7 節。
2. 容許清單的寫法。逐像素比對的容許範圍怎麼表達。
3. 後端服務與排程任務的可重現性怎麼比對。見第 5 節。
4. 要求二的並行污染什麼時候要重新決定。見 3.3。
